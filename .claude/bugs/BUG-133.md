## 解決 (2026-06-22 検証、engine 変更なし)

本 BUG が要求した `drainAiEffectPicks` の player guard は **BUG-138 (engine拡張 wave#2 cluster2 X8)
で実装済** であることを確認した。

- **guard** (`src/engine/effect/apply-pick.ts` drainAiEffectPicks): `humanSide !== null && pending.player
  === humanSide → i++ continue` (queue に温存、同所有者内 FIFO 維持)。`__humanPlayerSide` は
  `src/App.tsx:73` で human play 時 `'self'` / spectator・smoke は `null` (= 従来挙動 byte-equal)。

- **driver 連携** (`src/ui/hooks/useOppTurnDriver.ts`): 決定 modal pending 中は再入しない (L56)、
  playTurn が `paused:{humanPick:true}` を返したら `surfacePendingSideChannels()` で modal へ転送し停止 (L76-80)、
  modal 解決後に resume (L192-215)。CPU 進行は human modal 待ちで deadlock せず正しく停止/再開する。

- **回帰ガード**: `tests/engine/effect/bug-138-drain-ownership.test.ts` (6 ケース) —
  self所有 pending 温存 / opp所有 drain / human の後ろの AI pending も drain (FIFO skip) /
  playTurn humanPick pause で move 0・横取りなし / humanSide=null 回帰 byte-equal。

→ 本 BUG 起票時 (2026-06-12) の「先頭採用で自動消化」は現コードでは発生しない。新規修正不要。

## 概要

`drainAiEffectPicks` (src/engine/effect/apply-pick.ts) は `pending.player` を見ずに
`__pendingEffectPickQueue` 全件を heuristic で順次解決する。useOppTurnDriver → ai/policy 経由で
CPU ターンの move ごとに呼ばれるため、**human 所有の pending pick が CPU ターン中に push されると
modal に届く前に先頭採用で自動消化**される。

## 影響範囲

- 【相手ターン中】trigger を持つ「まで」型 deck-look (PR084/PR090: 【相手ターン中】【現場リムーブ時】
  look-1→hand)。BUG-132 GAP-1 の decline channel (chooseMatch:'upTo') を付与済みだが、
  相手ターン中に発火した場合は本 gap により human に選択が surface されない (= 従来の force-add
  相当で消化、**現状互換であり回帰ではない**)
- 同様に相手ターン中に発火する human 反応の pick 全般 (構造上)

## 期待動作

humanSide の pending は drain せず store へ流し、CPU ターン中でも modal で選択させる
(または turn 終了時に surface する設計判断)。

## 修正方針

`drainAiEffectPicks` に `pending.player === humanSide → skip (queue に残す)` の guard を追加し、
useOppTurnDriver 側で surfacePendingSideChannels が拾えるようにする。AI 進行の block 防止
(human modal 待ちで CPU turn が止まる) の UX 設計を含めて別 wave で対応。

## 防止策

- pick channel 新設時は「誰が解決主体か (player)」と「どのループが drain するか」を必ず対にして確認する
