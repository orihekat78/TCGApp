# CPU AP pick left the match on the opponent-turn overlay

## Expected

When the CPU resolves B09075 a2, its AP target pick must complete without a
human UI prompt. The driver must then take the next CPU step or return control.

## Actual

Row 015 attempt 3 logged `effect:charModifyAP:awaiting-pick` and then the AP
`+2000/turn` result, but the public UI stayed on `相手のターン処理中` for over
7 seconds without a human-selectable control.

## Evidence and RCA

- Public desktop UI and LogPanel evidence only; no state inspection or dispatch.
- Existing uncommitted `src/ai/policy.ts` drains CPU-owned effect choices before
  returning a step to the opponent driver.
- Its focused regression test covers B09075 a2 and passed: 6 tests.
- Attempt 4 used a new desktop UI session and reproduced the same terminal
  overlay after the public log showed `effect:sceneEnter:awaiting-pick` and
  `effect:charModifyAP:awaiting-pick`, followed by the AP result.
- Therefore the focused policy test proves only the step-level behavior; it
  does not prove that the UI opponent-turn driver drains the resulting flow.

## Fix, prevention, and horizontal check

- `surfacePendingSideChannels` now transfers only human-owned effect picks and
  choices into the human UI store. CPU-owned decisions remain for the AI policy
  drain, so `driveOppTurn` does not wait on an unreachable modal.
- RED→GREEN regression: CPU-owned pick and choice were each surfaced before the
  fix, then remain queued after it; B09075 a2 and the human-owned pause path
  stay covered in `tests/ai/step-turn-human-deck-decision.test.ts`.
- Focused verification: 8 tests in that file plus the existing case-resolved
  human-pick driver test passed (9 total).
- Same-pair public-UI rerun passed: row 015 reached `YOU LOSE / 事件解決!`
  after CPU effect chains, a human hand-removal decision, and an action/cut-in.
  The opponent-turn overlay cleared and control returned before the final result.
