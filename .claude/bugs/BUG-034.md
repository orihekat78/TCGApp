## 期待動作

`dispatchEngineAction({ type: 'actionAgainstCase', ... })` 経由でアクション[事件] を実行すると:

1. `flow.actionCase.removeOpponentEvidenceTop` 内で `event.emit('evidence:remove-by-action', { player, ev })`
2. `src/engine/listeners/hirameki.ts` の listener が発火 → `_pendingHiramekiSideChannel` populate
3. `dispatchEngineAction` 内の `_drainPendingHirameki()` が値を返す
4. `store.setPendingHirameki(side)` で zustand に転送
5. `useGameStateStore.getState().pendingHirameki` で UI / E2E から参照可能

→ `useHiramekiFlowDriver` が pendingHirameki を検知 → fire/skip choice → `hiramekiResolve` dispatch で効果解決

## 実動作 (vite dev mode)

E2E (Playwright + vite dev server) で `dispatch(actionAgainstCase)` を実行しても `pendingHirameki` が **null** のまま。

Round 4j 探索で確認:
- 直接 `__game.event.emit('evidence:remove-by-action', ...)` は listener fire + side-channel populate **成功** (Module C を経由)
- `dispatch({type:'actionAgainstCase', ...})` 経由は side-channel に値が到達 **しない** (Module D ≠ C と推測)
- `tests/integration/hirameki-e2e.test.ts` (jsdom/vitest) は **正常動作** → 本番ロジック自体は正しい

## RCA

`_pendingHiramekiSideChannel` は `src/engine/listeners/hirameki.ts` の **module-level mutable variable** (singleton)。
vite dev mode で同モジュールが異なる import path (`@/engine/listeners/hirameki.js` vs `'../../engine/listeners/hirameki.js'` vs `'./engine/listeners/hirameki'`) で参照されると、TypeScript の `.js` 拡張子付き alias と相対パスの相互作用で **module instance が複数生成** され、side-channel state が共有されない可能性。

- `engine/index.ts`: `import { registerHiramekiListener } from './listeners/hirameki.js';` → Module C にて listener 登録
- `useEngineDispatch.ts`: `import { _drainPendingHirameki } from '@/engine/listeners/hirameki.js';` → Module D の drain を呼ぶ
- Module C の side-channel に値が入っても、Module D の drain は Module D の (常に空の) side-channel を読む

## 修正方針 (別 Round 4j-fix で実装予定)

### Phase 1: 現状確認 + 再現
1. `npm run dev` で実機ブラウザを開き、action[case] → 証拠リムーブ → pendingHirameki の流れを手動で再現
2. ブラウザ DevTools で `import.meta.url` を listener 内 + drain 内で出力し module 同一性を確認
3. misread side-channel も同じ症状を示すか確認 (`useEngineDispatch.ts` L28 周辺は misread も同じ pattern)

### Phase 2: 修正
4. 候補 A: side-channel 状態を `globalThis.__hirameki_side` 等の **真の global** に移動 (module instance 分離を回避)
5. 候補 B: `_drainPendingHirameki` 等を `engine` namespace から re-export し、UI 側は `engine._drainPendingHirameki` 経由で必ず同 module 参照
6. 候補 C: vite config に `dedupe: ['src/engine/listeners']` 等で重複防止 (要 vite 仕様調査)

### Phase 3: 回帰確認
7. `tests/integration/hirameki-e2e.test.ts` は引き続き pass
8. E2E `hirameki-draw.spec.ts` を **元の 7 test 構成** (shape + fire + skip + negative) に拡張、4 件追加 + 全 pass
9. 手動 Playwright プレイで hirameki UI 動作確認

## 防止策

- mutable module-level singleton state を持つ場合、import path 揃え or globalThis 経由を **共通クラス checklist** に明記 (`.claude/specs/card-addition-checklist.md` に追記)
- 新規 side-channel 追加時、ブラウザ + jsdom 両方で 1 dispatch fire を必ず E2E で確認
