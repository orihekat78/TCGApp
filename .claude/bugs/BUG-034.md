## 修正 (Round 4j-fix)

### 真の原因: useHiramekiFlowDriver の auto-resolve

[src/ui/hooks/useHiramekiFlowDriver.ts](../../src/ui/hooks/useHiramekiFlowDriver.ts) は `pendingHirameki.player === 'opp'` のとき `HeuristicPolicy.chooseHiramekiTrigger` 経由で **自動的に hiramekiResolve dispatch**。E2E test が dispatch 完了後に `pendingHirameki` を読み出した時点では既に auto-resolve 後の null になっている (rules/10: AI が opp 側のヒラメキを自動判定するのは正しい仕様)。

Round 4j の初回診断では「vite module isolation」を疑ったが、debug counters で:
- `__hiramekiListenerFired: 1` (listener fires correctly)
- `__hiramekiWriteCount: 3` (write count)
- drainLog 2 件 (1 回目は value、2 回目は auto-resolve の dispatch 経路)
- `storePending: {...}` (auto-resolve 前は store にセットされている)

を確認、auto-resolve が真の原因と判明。

### 修正 1: fixture で self を hirameki owner にする (test-side workaround)

E2E test の fixture を反転: **opp を attacker、self を hirameki owner** に。
`useHiramekiFlowDriver` は `pending.player === 'self'` の場合 early return (UI modal 待ち)、auto-resolve しない → test が pending を観測可能。

- `dispatchAction({ type: 'actionAgainstCase', byUid: 'partner:opp', targetPlayer: 'self' })`
- fixture: `opp.partner.state='active'` + `self.evidence[0] = 対象 cardId` + `self.deck >= 5` + `self.case 事件編`

### 修正 2: side-channel を globalThis 経由に (engine 側の防御的改善)

[src/engine/listeners/hirameki.ts](../../src/engine/listeners/hirameki.ts) の `_pendingHiramekiSideChannel` (module-level mutable) を `globalThis.__pendingHirameki` に変更。同 module の複数 instance (vite dev mode で起こり得る) でも state が共有される。`misread.ts` も同パターンで修正。

これ自体は BUG-034 の必要条件ではなかった (test workaround で十分) が、将来の module duplication に対する防御として保持。

### 修正 3: engine namespace re-export (import 統一)

[src/engine/index.ts](../../src/engine/index.ts) で `_drainPendingHirameki` / `_resetPendingHirameki` / `_drainPendingMisread` / `_resetPendingMisread` / `_resetHiramekiRegistered` を re-export。
[src/ui/hooks/useEngineDispatch.ts](../../src/ui/hooks/useEngineDispatch.ts) の import を `@/engine` に統一 (旧: `@/engine/listeners/hirameki.js` / `@/engine/listeners/misread.js`)。

import path 統一による vite module dedup を確実にする副次効果。

### 検証

- E2E spec `tests/e2e/patterns/hirameki-draw.spec.ts` を 3 → 7 tests に拡張:
  - 既存 shape (D08013 + D08024) + non-hirameki negative (D08015)
  - **新**: 各カード fire/skip path (4 tests) — pendingHirameki populate → hiramekiResolve('fire'/'skip') → self.hand delta 確認
- unit 1467 PASS + 1 skipped (回帰なし)
- E2E 27 → 31 PASS + 1 skipped (+4)
- smoke 525/475 完全維持

## 期待動作

E2E (Playwright) で:

2. dispatch `actionAgainstCase` (byUid='partner:opp', targetPlayer='self')

5. `useHiramekiFlowDriver` は `pending.player === 'self'` のため auto-resolve せず early return

7. test が `hiramekiResolve('fire'|'skip')` を明示 dispatch
8. fire → `self.hand +1`、skip → `self.hand 不変`、両方とも `pending` クリア ✓
