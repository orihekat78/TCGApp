## 2026-06-06 再調査 (タスク E) — throw は既に解消済

起票時 (2026-05-28) の「実動作: 2 体目 sceneEnter が mutate.scene.enter で **throw**」は、
**2026-06-04 switch-on-effect-enter** (BUG-106、atom-handlers sceneEnter の満杯ガード追加) で
**解消済**であることを実コードで確認した:

- 満杯 (5枚) + `switchRemoveUid` 無し → **skip** (rules/15「可能な限り」、AI/未指定経路。throw しない)
- 満杯 + `switchRemoveUid` 有り → `mutate.scene.switchEnter` (既存1枚退場 + 登場 = **条件2 の結果に到達**)

`mutate/scene.ts enter()` の throw は防御的 invariant で、atom-handler 経由 (全カード効果) では
満杯時に enter() を呼ばずガードするため **到達しない**。検証: `tests/engine/effect/bug-083-multi-entry-switch.test.ts`
(現場4枚 + 2体 sequence 登場 → throw せず scene≤5 / overflow に switchRemoveUid を与えれば両方登場)。

**結論**: BUG-083 の crash 懸念は解消済。専用 `sceneMultiEnter` (2体を真に同時 enumerate して
1回の switch を選ばせる) は **該当カード0** のため未実装 (骨格凍結原則)。per-step switch で
条件2 の結果は到達可能 (human は 2 体目登場時に退場キャラを選ぶ)。multi-entry カードが
実装される場合のみ、下記 Option B の sceneMultiEnter を検討する (latent refinement)。

## 仕様 (rules/20-color-and-switch.md §スイッチ)

スイッチ発動条件は **2 つ**:

1. 現場が埋まっている (5 枚) 場合
2. **キャラを 2 枚以上同時に登場させる際に現場の上限を超える場合**

## 期待動作

例: 現場 4 枚 + effect (キャラ A + キャラ B を同時登場) → 4 + 2 = 6 で上限超 →
スイッチ発動 (既存キャラ 1 枚をリムーブして 5 枚に維持)。

## 実動作 (修正前)

- [src/engine/effect/atom-handlers.ts:374](../../src/engine/effect/atom-handlers.ts#L374) `sceneEnter` atom は単一 cardId のみ処理
- Effect の sequence 内で 2 体 enter する場合:
  - step 1: 現場 4 → 5 (OK)
  - step 2: 現場 5 → 6 → [src/engine/mutate/scene.ts:42-45](../../src/engine/mutate/scene.ts#L42-L45) で **throw** (scene full)
- 条件 2 のスイッチ flow (user に「どれを残すか」を聞く) が未実装

## 想定修正 (将来)

複数案あり:

### Option A: sceneEnter atom に switchMode 追加
`sceneEnter` の args に `{ allowSwitch: true, switchPicker?: ... }` を追加し、enter 直前に
`scene.length >= 5` なら switch picker を起動。Effect descriptor 内で複数の sceneEnter を
sequence した場合、各 step で個別に switch 発動。

### Option B: 新 atom `sceneMultiEnter` 追加
`{ player, cardIds: [...], n: number, switchPicker: ... }` で複数登場をアトミック化、
合計 entry 数が 5 超過なら一括 switch を user に選ばせる。

### Option C: 後処理 hook で 5 枚超過を検出 → switch 発動
Effect 全 step 解決後に invariant pre-check し、scene.length > 5 ならその時点で switch UI
起動。complete だが flow が複雑。

優先度低 (MVP デッキで multi-entry を持つカードは存在しない) のため、当面 latent
として保留。将来 multi-entry カードを実装する際に上記いずれかを採用。
