## 概要

既定で全ユーザーに配布される `SAMPLE_DECK_OPP`(警察・標準) の40枚デッキ内に、**事件カード D11021**
(千速と重悟の婚活パーティー, type=事件) が ×3 混入していた。公式ルール (02)「デッキにはキャラとイベントのみ。
パートナー・事件は入れられない」に違反。さらに `engineStub.validateDeck` は `type==='partner'` のみ拒否し
**`type==='case'` を検証していなかった**ため、この違法デッキが `ok` 判定されていた。
`customGameStart.toEngineDeck` は全 entry を mainCards 展開するので、D11021 が **caseId と同時に main にも**
混ざる二重使用状態だった。

## 期待動作 vs 実動作 (修正前)

| 入力 | 修正前 validateDeck | 修正後 |
|------|-----------------|-------|
| SAMPLE_DECK_OPP (D11021事件×3 含む) | **ok (バグ)** | データ修正で混入解消 |
| 任意デッキに事件カードを1枚追加 | **ok (バグ)** | 「デッキに事件は入れられません: …」 |

## 修正

1. **データ**: `sampleDeck.ts` の `SAMPLE_DECK_OPP` から D11021×3 を除去し、題材キャラ
   (萩原千速/横溝重悟/松田陣平) を各2→3枚に増やして40枚を維持 (cardId 集計でも各3以下、合法)。
2. **検証強化**: `validateDeck` のループに `type==='case'` 拒否を追加 (partner と同列)。
3. **事件スロットの導入**: `DeckRecord` に `case`(事件 cardNum) を追加 (rules/02: パートナー1+事件1+40)。
   `validateDeck` が事件1枚必須を検証、DeckEditor に事件選択スロットを新設、`customGameStart` は
   `deck.case` を使用 (旧 partner→case 推定はマイグレーション/未設定時の fallback に縮退)。
   `decksStore` を v2 に上げ、永続済み旧デッキへ `defaultCaseForPartner` で case をバックフィル。

## 水平展開

- 全 DeckRecord リテラル (sampleDeck の2件のみ) に `case` を付与済。型必須化で漏れは tsc が捕捉。
- `SAMPLE_DECK`(d08) も全数確認 → 40枚・全キャラ/イベント・同ID≤3で合法 (混入は OPP のみ)。
- 旧 `inferCaseId` ハードコードマップは `defaultCaseForPartner` に統合 (cardPool)。

## 防止策

- e2e `deck.spec.ts` / `engine-stub.spec.ts` でサンプルデッキが「検証 OK」を維持することを確認。
- 新しいデッキ既定値・インポートは必ず `validateDeck` を通す (パートナー/事件/40枚/同ID≤3 を一括ゲート)。

## 追記 (敵対的レビュー検出): migration の修復不足 (高)

初版の `decksStore` v2 migrate は `case` をバックフィルするだけで `cards` を浄化せず、**v1 から
アップグレードした既存ユーザーの永続 sample-d11 に違法な D11021×3 が残存**していた。結果:
(A) Setup で「事件は入れられません」検証 NG (旧版では valid だった回帰)、(B) TutorialScreen の練習/章ガイドは
sample-d11 を再検証せず `customGameStart` するため、3枚の事件カードを混ぜたデッキで対戦が始まる (rules/02 違反)。
→ migrate を強化: 既知サンプル(sample-d08/d11)は最新の正データで cards を上書き、カスタムデッキは
パートナー/事件カードを除去。e2e `deck.spec.ts` に v1→v2 修復の回帰テスト追加。

## 教訓

「UI ガード ≠ 検証ゲート」。DeckEditor が事件追加をブロックしても、永続/インポート/手編集の DeckRecord は
`validateDeck`(=isPlayable) が唯一の真の関門。配布データ自身がルール違反だと検証穴が顕在化する。
スキーマ追加時の migration は「新フィールド補填」だけでなく「旧データの不正値の浄化」まで責務に含める。
