## 期待動作

「自分のFILEエリアにあるカードを上から1枚手札に加える」(verb `filePopToHand`) は、
FILE 最上部 (非アシストパートナー) の **実 cardId** を手札に加え、`file:pop` を emit する
(ネクストヒント next-hint.ts:66-74 と同一 semantics、rules/12)。

## 実動作 (修正前)

- `FILE_CARD_BACK_PLACEHOLDER` ('card-back' 文字列) を手札に push → 使用不能なゴーストカード化
- `file:pop` も未 emit (B05050「FILEのカードを手札に加えたとき」が永久不発になる構造)
- Round 3 で FileCard が cardId を保持するようになり next-hint 側は修正されたが、verb 側が取り残された

## RCA

同一機能 (FILE→手札) が next-hint flow と effect verb の 2 経路に分かれており、
Round 3 の修正が flow 側のみに適用された (twin-path の片側 stale 化)。
verb 使用カードが当時 0 枚だったため検出されなかった (latent)。

## 修正

- atom-handlers.ts `filePopToHand`: popped.cardId を hand.add + `event.emit('file:pop', {player, popped})`
- popped 無し (FILE 空/アシストパートナーのみ) は `__chainStepNoApply=true` (PR100/B04068 Q&A
  「FILE に無ければ『そうした場合』以降は解決できない」)
- 既存テスト atom-handlers.test.ts の placeholder assert を実 cardId assert に更新 (fixture も cardId 付与)

## 水平展開

- 他の twin-path 走査: fileAdd (auto-phase / effect) → effect 経路にデッキ0リフレッシュ guard 欠如を
  発見し同時修正 (rules/14「FILEに置く」=リフレッシュ後残り解決)。auto-phase 経路は仕様通り (先攻初手1枚等) で不変
- cost `fileFrom` にも別の stale (戻り値破棄) を発見 → [[BUG-129]] として起票・修正

## 防止策

- 同一ゲーム操作を flow と verb の両方で実装する場合は mutate 層 primitive に寄せ、
  挙動差は呼出側の明示 opt (引数) にする — リファクタ計画 (2026-06-12 ユーザーゴール) の対象項目
