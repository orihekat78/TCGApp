## ユーザー指摘

> ワークフローを確認しました。処理が複雑になっていますね。私としては処理は単純にできると思っています。例えば a1 については、ネクストヒントなどを考慮に入れなくても現場エリアのほうで登場有無を確認できれば登場時効果の起爆にはなりますよね？

## 期待動作

カード処理ワークフロー図は **カード固有の意味** (rules/ 用語に基づく挙動・atom レベルの効果・カード固有の分岐) のみを表現し、エンジン内部の関数名・event emit 等の実装経路は隠蔽する。これは骨格凍結原則 ([CLAUDE.md L78-92](../CLAUDE.md)) の「カード視点での抽象化」と整合する。

## 実動作 (修正前)

`.claude/specs/cards-analysis/D08015-workflow.md` の a1 (登場時効果) フローチャート (Mermaid) に以下が漏れ込み、図が 131 行に肥大化 ([CLAUDE.md L172](../CLAUDE.md) の 100 行制約超過):

- **登場経路 3 分岐** (`handUseCard` / `nextHint` / `sceneEnter` atom) — 実装上は全経路が `mutate.scene.enter` + `event.emit('enter')` の単一点に集約済み、カード側は経路を意識する必要なし
- **エンジン内部経路** (`event.emit` / `listeners.triggered.runTriggered` / `collectCardsInPlay`) — ブラックボックスでよくカード仕様に無関係
- **解決パイプライン** (`resolveEffectPicks` / `event.queue` / `runAllUntilEmpty`) — 骨格固有の処理でカード固有の意味なし

副次問題: Mermaid 構文エラー (ノードラベル内の `(`, `[`, `'` が形状区切り文字と衝突、`<code>` 未サポート) でレンダリング失敗。

## RCA

本質は **「簡素化できるよう考えていなかった」** という思考プロセス上の欠落で、結果として **「簡素化できる処理を複雑に書いた」** という症状になった。3 つの要因が連鎖:

1. **抽象化レイヤーを意識しなかった** — エンジン実装を忠実にトレースしすぎ、internal API 名がカード仕様図に流入。カード視点で意味があるのは「どの rules/ を実行するか・どの atom を使うか・カード固有分岐はどこか」の 3 点だけで、`engine.flow.*` や `event.emit` はノイズ。
2. **「集約点」を見抜こうとしなかった** — 3 経路を分岐として描いた時点で「集約できないか」を考えるべきだった。「描き終わった図が複雑だったら設計に問題がある」というシグナルを見逃した。
3. **Mermaid 構文への基本的な無頓着** — ノードラベルを `"..."` でエスケープする基本を怠り、レンダリング失敗に気づかなかった (副次)。

## 修正

a1 / a2 図を「カード固有挙動のみ」の最小フローに書き直し:

- a1: 登場 → step 1: 1 ドロー → step 2: 1 リム → 完了 (4 ステップ)
- a2: コンタクト発生 → 手札の D08015 を cutin 使用 → actor AP +1000 → コンタクト終了で解除 (4 ステップ)

engine 内部の責務は全て図から除外し、図直後の注釈で補足:

- draw 内の deck-0 / refresh / リムーブ 0 → 敗北 (rules/14) は `draw` atom の責務 (BUG-036 配線)
- step 2 の選択者分岐 (human → EffectPickerModal / AI → heuristic) は `resolve-picks` の責務 (BUG-053/054 配線)
- 変装による登場では `enter` hook 不発火 (rules/09)
- 登場経路 4 種 (手札使用 / ネクストヒント / 効果による登場 / スイッチ) は `enter` hook に集約済み

**表現形式の変更**: Mermaid → ASCII フロー (```text ブロック + box-drawing characters) に切り替え。理由はユーザー環境の Markdown プレビュー (Mermaid 拡張機能) で 4 ノードの最小構文すら描画されない問題があり、環境依存性を排除して「絶対に見える」表現にしたため。
