## RCA

BUG-075 の修正は「sequence 内で最初の pattern B atom 用 side-channel を保持」する。これにより step 2 modal は出るが、ユーザーが step 2 を解決した後、**step 3 用に新たな side-channel を set する仕組みがない**:

- triggered listener は sequence 全体を 1 回 queue するだけ (resolveEffectPicks は 1 回しか走らない)
- effectPickResolve dispatch は 1 atom (= step 2) を resolved 状態で再 queue するだけ
- step 3 atom は **target=pick query object のまま** queue 内に残り、atom-handler で normalizeTargetToString → undefined → awaiting-pick log + skip
- side-channel は再 set されない → UI に modal 出ない

## 修正方針 (2 案)

### 案 A: effectPickResolve で再 resolveEffectPicks + 再 queue

`PendingEffectPickSide` に `abilityEffect: Effect` (元 ability effect tree) を追加。effectPickResolve で:

1. resolved atom を queue + runAllUntilEmpty
2. 元 abilityEffect を再 resolveEffectPicks (humanChooser=true) で walk
3. 新たな side-channel が set されれば store.pendingEffectPick 更新 → UI が次 modal 表示

問題点: 再 resolve すると step 2 (実行済み) も再度 walk されて側チャネル set される。実行済み step を skip するマーカーが必要 (effect tree への書き込み or 別 state)。

### 案 B: triggered listener が sequence の各 step を個別 queue

設計変更だが root cause 治療。

1. triggered listener が `effect.kind === 'sequence'` の場合、各 step を独立した event.queue entry として積む
2. runAllUntilEmpty が各 entry を順次処理 (resolveEffectPicks は entry 単位で再走)
3. step 2 entry: side-channel set → atom skip
4. modal 解決 → step 2 atom 単体実行 → entry 完了
5. step 3 entry: resolveEffectPicks 再走 → 新たな side-channel set → modal 表示

問題点: pendingEffects 関連の数値・順序が変わる、smoke 1000 への影響 verify 必要。

→ **案 B が root cause 治療として推奨** だが影響範囲が広いため、ユーザー判断待ち。
