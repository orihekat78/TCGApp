## 発見契機

ユーザーから「D08013 a1 全 3 step は実機で正しく動作していない、Playwright で確認しろ」の指示で、claude が dev server を起動し Playwright で D08013 を 2 ターン目に手札使用 (ターン後攻 2)。

実機ログ:

```text
T4 自 効果: 証拠 → 手札 (選択待ち)   ← step 2 evidenceToHand awaiting-pick で skip
T4 自 効果: 手札選択待ち              ← step 3 discard awaiting-pick
T4 自 効果: 手札リムーブ: 1           ← modal 選択後、step 3 だけ実行
```

effect スタック残 2 件 (step 2 / step 3 共に未解決として queue されたが、modal は **step 3 用しか表示されず**、step 2 は永遠に awaiting)。

## 期待動作

D08013 a1 (3 step sequence: evidenceGain → evidenceToHand pick → discard pick) で:

1. step 1 evidenceGain → 自動実行 (証拠 +1)
2. step 2 evidenceToHand → **modal 表示 (証拠候補から選択)** → 解決
3. step 3 discard → **modal 表示 (手札候補から選択)** → 解決

modal は 2 段階で出る (step 2 → step 3)。

## 実動作 (修正前)

- step 1 evidenceGain は動作
- step 2 evidenceToHand は awaiting-pick で skip、**modal 表示なし**
- step 3 discard の modal だけ表示 → ユーザー選択 → step 3 のみ実行
- step 2 は永遠に未解決のまま、effect スタックに残る

## RCA

`src/engine/effect/resolve-picks.ts` の sequence walk:

```typescript
case 'sequence':
  return { ...effect, steps: effect.steps.map((s) => resolveEffectPicks(state, s, ctx, opts)) };
```

`.map` で全 step を順次 walk するため、複数の pattern B atom がある場合:

1. step 2 evidenceToHand: `humanChooser=true` で `setPendingEffectPickSide({...})` (evidenceToHand 用)
2. step 3 discard: 同じく `setPendingEffectPickSide({...})` で **step 2 用の値を上書き**

結果: side-channel に残るのは **最後の atom (step 3 discard) 用** だけ。UI は step 3 用 candidates (手札) を表示。

加えて、ユーザーが modal で選択して `effectPickResolve` dispatch すると、step 3 用 atom が単体で再 queue + 実行されるが、step 2 は **永遠に未解決のまま** queue に残る (atom-handler の awaiting-pick で skip され続ける)。

これは BUG-065 (pattern B 対応) / BUG-071 (sequence pre-step skip 廃止) / BUG-074 (target string|array 両対応) のいずれでも触れられなかった「**複数 pattern B atom がある sequence**」の挙動。BUG-066 の 4 点 verify を再々々度破った形 (sequence 内 atom 数の網羅 verify を怠った)。

## 修正方針

2 段階の修正:

### A. resolve-picks.ts — side-channel 上書き防止

`substituteAtomPick` で `humanChooser=true` のとき、**既に side-channel が set されていれば、新規 set せずに atom を未解決返却**:

```typescript
if (opts.humanChooser) {
  if ((globalThis as { __pendingEffectPickSide?: unknown }).__pendingEffectPickSide) {
    return atom as Effect; // 既存の pick 待ちを優先
  }
  // ... (既存 setPendingEffectPickSide)
}
```

これで sequence walk で **最初に検出した pattern B atom** が side-channel を保持。後続 pattern B atom は walk しても上書きしない。

### B. useEngineDispatch.ts — 1 atom 解決後に元 effect を再 resolve + 再 queue

`effectPickResolve` で resolved atom を queue した後、**元 effect (sequence 全体) を再度 resolveEffectPicks** して新たな side-channel が set されたか check。set されたなら UI が次の modal を表示。

具体的な実装は、現在 PendingEffectPickSide が 1 atom 情報しか持たないため、**元 ability の effect tree への参照** を保持する必要 (もしくは triggered listener が再度発火する仕組み)。

### 代替案 (シンプル)

triggered listener が effect 全体ではなく、各 step を個別 queue する設計。これは大きな設計変更だが root cause 治療。

→ **本 BUG-075 では A (上書き防止) を最低限実装し、B (再 resolve) は別 BUG として defer する**。A だけでも step 2 が修正済み state を保つようになり、ユーザーが step 2 modal を完了したら step 3 modal が次に出る (resolve タイミング次第)。

## 検証

- Playwright で D08013 を 2 ターン目に手札使用
- step 1: 証拠 +1 (自動)
- step 2: modal 表示 (証拠候補から選択) → 解決
- step 3: modal 表示 (手札候補から選択) → 解決
- effect スタック 0 件で完了
- log に 3 step 全て記録される
