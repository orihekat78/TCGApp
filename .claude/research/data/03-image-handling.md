# 03. 画像ハンドリング設計

## 法務制約（再確認）

`.claude/research/legal/04-recommendation.md` より:

- **画像はリポジトリに同梱しない**
- **実行時に公式URLからフェッチ + ローカルキャッシュ**
- 完全ローカル運用が前提

## 公式画像URL構造

```
https://www.takaratomy.co.jp/products/conan-cardgame/storage/card/{filename}
```

- `{filename}` は `main_path` または `sub_path` フィールドの値
- 例: `1743743093420786.jpg`
- ファイル名はハッシュ的（連番ではない）→ 別途マッピング必要

## main vs sub の違い（推測）

| フィールド | 推測される用途 |
|-----------|---------------|
| `main_path` | カード表面画像 |
| `sub_path` | カード裏面 or サムネイル |

実際の表示確認が必要（実装時に検証）。

## キャッシュ戦略

### ストレージ選択肢

| 方式 | メリット | デメリット |
|------|---------|-----------|
| **IndexedDB** | ブラウザ内で完結。Blob格納可 | 容量制限（通常数百MB） |
| ファイルシステム（Node側） | 容量無制限・直接配信可 | サーバ層必要（案A前提） |
| Service Worker Cache | オフライン対応・自動 | 制御が複雑 |

### 推奨: ハイブリッド

```
[初回起動]
  ↓
[サーバ側で公式から一括ダウンロード]
  → .cache/images/{cardNum}.jpg に保存
  ↓
[クライアント要求時]
  ↓
[ローカルキャッシュにあれば即配信]
[なければ公式から都度フェッチ→キャッシュ→配信]
```

## 画像の使い分け

### MVPでは
- 解像度: 公式の元解像度をそのまま使用
- 必要箇所:
  - 手札・現場のカード（縮小表示）
  - カード詳細モーダル（フルサイズ）
  - 推理・アクション中のアニメーション

### 性能対策（後続フェーズで詳細化）
- 縮小サムネイルを別途生成（クライアント or ビルド時）
- WebP変換でサイズ削減
- 遅延読込（Intersection Observer）

## オフライン挙動

- 全画像が `.cache/images/` に揃っていればオフラインでも遊べる
- 起動時に「画像未取得」を警告 → ユーザーが「ダウンロード」を選ぶ

## 著作権表記の常時表示

`© 青山剛昌／小学館 © TOMY` を起動画面・対戦画面の隅に常時表示する。
これは権利者への敬意 + 万一のトラブル時のリスク軽減。

## エラーハンドリング

- 公式が画像URLを変えた場合
  - HTTP 404 を検出 → 「カード画像なし」プレースホルダー表示
  - メタJSONを再フェッチして `main_path` を更新
- 公式サイトがダウン
  - キャッシュ済み画像のみ使用 → 警告表示
