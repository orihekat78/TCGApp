# B02022 鬼丸猛 grounding (2026-07-10, sonnet5)
> 状態: BLOCKED

## 印字
〚突撃［キャラ］〛（登場したターンからすぐにキャラを指定してアクションできる）
【ターン1】相手の現場にいるキャラがアクションするとき、このキャラを指定できる場合、必ず指定する。
【ヒラメキ】（証拠からリムーブされるときに発動する）カードを1枚引く。
公式Q&A 5件 (このカード専用の詳細裁定):
- 発動タイミング = 相手がアクションを行う時点で (**対象を指定するより先に**) 発動、指定できる
  場合は必ず指定。
- 【ターン1】は「指定できたか」に関わらず「アクションする」時点で消費 (=1回目のアクション宣言
  だけが対象、以降そのターン中は不発)。
- アクティブ状態の鬼丸猛はそもそもアクション対象になれない (rules/07 base) ので、この場合は
  他対象を指定してよい。
- スリープ/スタン状態が2枚以上いる場合は同時発動、指定は1枚のみ (アクションするプレイヤーが
  選ぶ)、残りは実行不能で無視、全て発動済扱いで当ターン再発動しない。

## engine gap (2026-07-09 調査を今回 code で再検証 — 結論は変わらず、記述をより正確化)
- `turnEffects.mustBeTargeted` (target-expander.ts `mustTargetCandidates`, line 198-211) は
  D11005 「挑発」が使う既存 primitive — だが **【宣言】+ sleepSelf コストで能動的に有効化**し、
  `scope:'opp-turn'` で相手ターン終了まで**継続的に**効く方式 (charSetTurnEffect 経由)。
  B02022 は宣言/スリープ不要で常在し、かつ「そのターン最初の1回だけ」しか強制しない —
  D11005 の継続フラグでは表現できない (常時 on にすると 2 回目以降のアクションも強制してしまう)。
- `action:pre-target` hook (`applyPreTargetExpansion`, target-expander.ts) は candidates() 内で
  **同期的に** scene を走査する既存経路 (Q&A の「対象指定より先に発動」というタイミング要件と
  一致する唯一の場所) だが、現状 `expandActionTargets` (対象を**追加**する) 用途のみ。
  「対象を**強制**する」ロジックは未実装。
- 真の欠落は「宣言コスト無しで常在 + そのターン最初のアクション宣言でのみ強制 + 結果に関わらず
  消費」という **一時性 (once-per-declare-commit)** の primitive。標準の `limit:{kind:'turn',n:1}`
  カウンタ (triggered.ts の event queue 経由) は非同期処理であり、`candidates()`/
  `mustTargetCandidates()` は UI/AI の合法手プレビューのために **宣言確定前に複数回呼ばれる
  純粋read関数** — この中で「消費」を書き込むと、プレビューのたびに【ターン1】を空費してしまう
  致命的な不整合を生む。

## 設計方針 (構造 gap — 3-5行)
1. 新しい宣言的 ability 形 (`trigger:{hook:'action:pre-target'}` + 新 atom 例
   `mustTargetSelfOnce`) を `mustTargetCandidates()` に追加 (`applyPreTargetExpansion` と同型の
   同期 scan)。判定は純 read: `turnEffects.<key> !== state.turn.number` の比較のみ (書込禁止)。
2. 実際の「消費」書込みは **`state-machine.ts` の `declare()` 内、対象が確定した瞬間** にのみ
   行う (pure read 関数からは絶対に書かない) — これにより UI/AI のプレビュー呼び出しでは
   消費されず、実宣言でのみ 1 回消費される。
3. 消費キーはカード固有 (uid ベース) + `state.turn.number` の組で管理し、標準
   `limit:{kind:'turn',n:1}` (event-queue 依存) とは別経路にする。
4. 同時に複数枚存在する場合の「1枚だけ選ぶ・残りは無視・全て発動済扱い」は各インスタンスの
   uid ごとに独立して消費フラグを立てることで自然に満たせる。

## tier + 理由
T3 (flow core / state-machine.ts の宣言確定タイミングと GameState 消費設計が絡む)。
フル4 lens + Playwright 相当 (プレビュー呼び出しでの誤消費が無いことを実機で確認する必要あり)。

## 罠
- 前回調査 (2026-07-09) の要約「mustBeTargeted は opp-turn clear / action:pre-target hook は
  expandActionTargets のみ処理」は正しいが、「primitive 不在」を mustBeTargeted 全体の不在と
  誤読しないこと — mustBeTargeted 状態フラグ自体は D11005 で shipped 済み。不在なのは
  「宣言コスト無し常在 + 初回のみ・宣言確定時にのみ消費」という variant のみ。
- 最優先の実装リスクは candidates()/mustTargetCandidates() の呼び出し回数 (UI 合法手列挙 / AI
  評価で 1 ターン中に何度も呼ばれる) と実消費タイミングの分離 — ここを誤ると「一度も指定
  できなかったのに勝手に権利を失う」逆方向のバグを生む。
