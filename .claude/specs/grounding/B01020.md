## DEFER 行の再判定 (dossier stale — 誤読を訂正)
dossier の DEFER 行「相手 actor 側 level-filter アクション禁止 aura 不在
(_canAction は opp 盤面 aura を走査しない)」は **actor 制限 (相手の低レベルキャラ自身が
アクションできなくなる) と誤読**していた。実際は **target 制限** (自分の低レベルキャラが
相手からアクション対象に指定されなくなる、いわゆる untargetable 系) であり、これは
**既に engine 実装・出荷済**。根拠:

- B04072 白鳥任三郎 (src/cards/ct-p04/B04072.ts、`_reuse/index.ts:1112/1755` 登録済) の印字文が
  **一字一句同型の文型**: 「このキャラがスリープ状態の場合、相手は自分の現場にいる
  レベル5以下の【青】とレベル5以下の【黄】のキャラを指定してアクションできない。」
  (levelMax/color filter 違いのみ)。B04072 は `continuousModifier.untargetableByActionAura`
  (mega-wave W6 step5, `src/engine/read/char.ts:198-223 auraUntargetableByAction`) で実装済 —
  この reader は **bearer と対象が同 side** (「相手は**自分**の現場にいる…」の「自分」=
  対象キャラの持ち主=bearer の持ち主、と一致) で候補を除外する既存関数。
- B01020 の Q&A「スタン状態の場合は条件を満たしていません」= `charStateIs` 単一状態一致
  (=== 比較、cond/eval.ts) で自動整合 (B04072 の設計コメントと同一の裁定文言)。
- B01020 の Q&A「ガードは可能」= B04072 の設計コメント既述の通り「ガード経路
  (state-machine.ts tryGuard) は target-expander.candidates() を経由しないため自動整合」。
  target 制限説でのみ Q&A が自然に説明できる (untargetable にしたのにガードは出来るのか、
  という混同されやすい点への釘刺し)。actor 制限説だと、そもそも「ガードは対象指定を伴わない
  行動」なのでこの Q&A の必要性自体が薄い。
- engine gap は無い — `untargetableByActionAura` primitive + `charStateIs` condition は
  B04072 で consumer 実証済、config だけ変えれば良い。

## 罠
- テキストの主語「相手は**自分の**現場にいる…」を「相手(actor)が自分(actorの)盤面のキャラを
  指定してアクション」= actor-restriction と読み違えやすい。実際は「自分」= B01020 controller
  (target 側)、「相手」=action する側、という通常の「自分/相手」規約 (カード所有者視点) 通りの
  target-restriction。B04072 の shipped 実装・Q&A が最終的な裏取り根拠。
- filter は levelMax のみ (color 指定なし) — B04072 の `{levelMax:5, color:[...]}` から
  color を単純に外すだけ、`matchOneFilter` の AND/OR 意味論変更は不要。
