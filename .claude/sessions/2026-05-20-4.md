## Phase 2: 修正適用 → debug → 真因発見

### Step 1-2: engine namespace re-export + import 統一
- `src/engine/index.ts` に `_drain* / _reset*` re-export (5 export)
- `src/ui/hooks/useEngineDispatch.ts` の import を `@/engine` に統一

### Step 3-4: spec 拡張 → fire/skip が失敗
- `hirameki-draw.spec.ts` を 3 → 7 tests に拡張 (各カード fire/skip + 既存 shape + negative)
- 実行: 4 tests fail (`pendingHirameki populated` assertion で null)

### Step 5: 詳細 debug → 真因判明
- `globalThis.__pendingHirameki` 直接観測 → `unset` (null)
- listener counter `__hiramekiListenerFired = 1` (listener 発火確認)
- writeCount = 3 / drainLog = 2 件 (1 回目 value、2 回目 null) / storePending = `{player:'self',...}` 一時的にセット
- **真因**: `useHiramekiFlowDriver` (`src/ui/hooks/useHiramekiFlowDriver.ts`) が `pending.player === 'opp'` で auto-dispatch `hiramekiResolve(fire/skip)` → test が pending を読む前に store クリア

### Step 6: fixture 反転で解決
- opp を attacker、self を hirameki owner にする: `dispatchAction({ type: 'actionAgainstCase', byUid: 'partner:opp', targetPlayer: 'self' })`
- `pending.player === 'self'` で driver early return → auto-resolve せず
- test が pending を観測 → 明示 `hiramekiResolve` dispatch で hand delta 確認

### Step 7: globalThis 防御
- `_pendingHiramekiSideChannel` (module-level) を `globalThis.__pendingHirameki` 経由に変更
- 同パターンを `misread.ts` にも適用 (`_pendingMisreadSideChannel` → `globalThis.__pendingMisread` — 本セッション未実装、Round 4k に持ち越し or 同 commit で実施)
