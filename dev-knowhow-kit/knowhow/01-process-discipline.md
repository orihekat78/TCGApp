# 01. プロセス規律 — 精度 > 速度

conan プロジェクトで最も効果が大きかった基本姿勢。CLAUDE.md の冒頭に置く。

## 原則

- **"おそらく" "多分" で進めない**。コード / 一次情報 / 実行ログを直接参照して根拠を確定させる
- 時短のための短絡（サンプル数縮小・水平展開省略・推測での判定）は禁止
- **速度 < 精度** を全フェーズで優先する
- LLM は「それらしい仕様」を捏造しがち。一次情報参照を義務化しないと必ず事故る

## セルフレビュー（ユーザーレビュー依頼の前に必須）

- [ ] 実装が要件通りか / ナレッジベース（rules/ 相当）と矛盾がないか
- [ ] エッジケースを考慮したか（→ 下記 5 分類）
- [ ] テスト・型チェック・lint が通るか
- [ ] **実機通し検証**（「画面表示確認 ≠ 機能確認」→ knowhow/06）
- [ ] バグ管理表更新（→ knowhow/03）
- 提出時は「セルフレビュー実施済」「水平展開調査完了」と明記する

## エッジケース 5 分類（ドメインごとに最初に定義し直す）

conan での 5 分類を例に、新ドメインでも「定番境界条件」を 5 つ最初に決める:

1. **0 件**（手札 0 / デッキ 0 / リスト空 / null）
2. **不可逆操作**（一方通行の状態遷移・取り消せない確定処理）
3. **状態相互作用**（特殊状態と通常処理の優先関係）
4. **数値の下限・マイナス**（下限なし仕様・0 以下での挙動分岐）
5. **複合・連鎖**（効果の引継ぎ・処理中の状態変化）

設計ドキュメントはハッピーパスのみで確定してはならない（最低 5 件のエッジケース列挙義務）。

## 水平展開調査（必須・最重要）

- 修正・追加した箇所と **同じ構造を持つ他の箇所** を必ず全件調査する
- 例: ある分岐のバグ修正 → 類似分岐の全件確認。あるモーダルの設計 → 他モーダルとの整合
- 調査結果は memory.md / セッションログに必ず記録
- **実績**: BUG-008（分岐欠落）の水平展開で別経路の同一バグを同 commit で発見・修正。
  逆に個別場当たり修正だった時期は重大バグ 5 件を 3 スプリント見逃した

## 設計レビュー 4 チェック（spec 確定の前提条件）

1. **網羅性監査**: ナレッジベース全ファイルを 1 件ずつ開き、設計への反映箇所を書き出す。
   触れない場合は「out of scope: 理由」を明示（「触れなかった」と「見落とした」を区別する）
   - 実績: 初版設計でこの監査により計 44 件の漏れが判明した
2. **エッジケース最低 5 件**（上記 5 分類）
3. **水平展開**: 類似構造の他箇所と整合させる
4. **状態完備性**: 全 state field が「いつ更新され、どこに表示されるか」の対応表を持つ（逆引き可能に）

## 「修正済」遷移プロトコル

バグや課題を「完了」にする前の必須 3 点（実事故由来: 完了宣言の翌日に同根の不具合報告）:

1. 関連ファイルの修正が実在することを Read で確認
2. 修正範囲周辺を `暫定|TODO|FIXME|未対応|仮対応|workaround` で grep
3. 残課題が見つかったら **別チケットを同時起票** しない限り「完了」へ遷移禁止

## ユーザー指摘 vs 一次資料の裁定プロトコル

ユーザーが「これはバグでは?」と指摘したとき:

- ローカル抜粋（二次表現）だけで反論しない。**必ず原文**（PDF / API docs / 規制原文）を取得し原文引用で裁定
- 裁定結果は判例集ファイル（`docs/clarifications.md` 相当）に「指摘引用 → 実装根拠 (file:line) → 原典根拠 → 結論」で蓄積
- 同じ質問が再来したら即答できる。抜粋自体の誤りとコード側バグの両方を発見した実績あり

## 移植のしかた

CLAUDE-template.md（templates/）に本内容の要約が組み込み済み。新プロジェクトでは
エッジケース 5 分類と「一次情報」が何か（API 仕様 / 法令 / 社内規程…）だけ差し替える。
