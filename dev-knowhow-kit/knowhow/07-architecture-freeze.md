# 07. 骨格凍結原則 — コア凍結 + 周辺拡張で修正範囲を収束させる

大量の個別機能（カード効果・プラグイン・テンプレート等）を載せる基盤を持つ
プロジェクトで、変更コストを時間とともに **収束** させるガバナンス。

## 骨格凍結原則

- **コア（基盤層）は原則編集禁止**。例外は 3 つだけ:
  1. 一次情報（公式ルール / 仕様）の変更時
  2. コア自体のバグ修正
  3. 動作不変の内部最適化
- **個別機能対応のためのコア修正は禁止**（これを許すとコアが無限に肥大する）

## 共通クラス運用（パターンの置き場）

- パターンが 3 回出現しても **コアにはプロモートしない**。`_shared/` 配下に共通クラス追加で対応
- 共通クラスは **破壊的変更禁止**。新パターンは「新クラス追加」（既存クラスの仕様変更ではなく）
- 共通クラスは必ずコアの公開 API を経由（コア内部アクセス禁止）
- 個別機能間の直接参照禁止（必ず共通クラス経由）

## 収束の見える化（数値ターゲット）

| 指標 | 初期 | 6 ヶ月後 | 1 年後 |
|------|-----|---------|--------|
| コア PR / 月 | - | 0 | 0 |
| 新機能追加時 touched files | 5 | 3 | 2 |
| 新機能追加時の修正行数 | 200 | 100 | 80 |

- **touched files が 3 を超えたら設計見直し** をルール化
- 宣言的 DSL（JSON シリアライズ可能な Effect Descriptor 相当）を最大限活用、
  カスタムコードは最終手段

## Capability Map（凍結コアが「できること」の一次文書）

コアを凍結すると「コアに何ができるか」が個別実装の判断基準になる。実コードから抽出した
単一リファレンスを生成・維持する:

- 全操作（verb）の正確な引数 / 全条件式 / フィルタフィールド / フック一覧
- **throw / stub / silent-no-op の注記つき**（「受理されるが無視される」が最悪の故障モード）
- 各記述に出典ファイル・関数名を必須にする（エージェントに書かせる場合も同様）
- コア拡張のたびに「この map は stale」と明記して再生成

## ゲート表（凍結コアが「できないこと」の一次文書）

- 3 部構成: ❌できないこと（throw / stub / フック欠落 / 条件欠落を分類）/
  ✅実機検証済み OK パターン（実証元ファイル名つき）/ ⚠落とし穴（受理されるが無視される系）
- **各ゲートに発見経緯（バグ ID・日付）を残す** — 後でコアが拡張されたとき stale 判定の根拠になる
- 「1 節でも該当したら見送り（DEFER）」の判定基準として使う

**なぜ必要か**: エージェント（と人間）が毎回同じブロッカーを再発見するコストを消すため。
実例: 「コードパスが在る（引数を受理する）だけでは不十分、semantics を実機確認せよ」
（受理されるが永久不発火だった参照が複数発見された）。

## DEFER 台帳（やらないと決めた事項の集約）

- 「できない / やらない」と判断した項目は捨てずに DEFERRED-INDEX.md へ:
  **項目 + 理由 + 再評価条件**
- 新規 defer を生んだ commit は必ず台帳に 1 行追加
- コア拡張のタイミングで台帳を見直し、解禁された項目を回収する
- 理由が書いていない defer は、後のセッションが「なぜやらなかったのか」を
  再調査するコストと stale 判断による誤実装の両方を生む

## 移植のしかた

1. プロジェクト初期に「凍結するコア」と「拡張置き場（_shared/）」の境界を 1 文で定義
2. CLAUDE.md に凍結原則 + 例外 3 つ + touched files 閾値を明記
3. コアが安定したら capability map とゲート表を生成（エージェント抽出でも可、出典必須）
4. DEFERRED-INDEX.md を作成し、見送り判断を理由つきで集約
